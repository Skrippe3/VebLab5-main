# Лабораторная работа №7

## Хранение файлов с использованием MinIO (Object Storage)

## Описание проекта

Проект представляет собой REST API на Flask с JWT-авторизацией, OAuth Yandex, Swagger-документацией, Redis, MongoDB и объектным хранилищем MinIO.

В рамках лабораторной работы реализовано хранение пользовательских файлов в MinIO без сохранения файлов в файловой системе приложения и без хранения бинарных данных в базе данных. В MongoDB сохраняются только метаданные файлов: имя, размер, MIME-тип, bucket, ключ объекта и владелец файла.

Лабораторная работа является продолжением предыдущих лабораторных работ №2–№6. Все ранее реализованные механизмы авторизации, refresh-токенов, cookies, OAuth, Redis и Swagger сохраняются и дополняются новым модулем работы с файлами.

Реализовано:

- подключение MinIO как S3-совместимого объектного хранилища;
- загрузка файлов через `multipart/form-data`;
- скачивание файлов через потоковую передачу;
- удаление файлов с использованием Soft Delete;
- хранение метаданных файлов в MongoDB;
- связь файла с пользователем-владельцем;
- защита доступа к файлам по JWT;
- проверка принадлежности файла текущему пользователю;
- загрузка и установка аватара пользователя;
- валидация MIME-типа и размера файла;
- кеширование метаданных файлов в Redis;
- Swagger-документация для новых эндпоинтов;
- Docker Compose инфраструктура с MinIO, MongoDB, Redis и Flask-приложением.

# Краткие теоретические сведения

## Объектное хранилище

Объектное хранилище — это способ хранения данных, при котором каждый файл представляется как отдельный объект. Объект обычно содержит сами данные, метаданные и уникальный ключ, по которому его можно получить.

В отличие от классической файловой системы, объектное хранилище не использует привычную структуру папок. Вместо этого файлы сохраняются в bucket и доступны по уникальному object key.

## MinIO

MinIO — это высокопроизводительное объектное хранилище, совместимое с Amazon S3 API. Его можно развернуть локально через Docker и использовать как отдельный сервис для хранения файлов.

В данной лабораторной работе MinIO используется для хранения загружаемых пользователем файлов и аватаров.

# Модель файла

Для хранения информации о загруженных файлах используется отдельная модель `File`.

Поля модели:

| Поле | Описание |
|------|----------|
| `id` | Уникальный идентификатор файла |
| `userId` | Идентификатор владельца файла |
| `originalName` | Оригинальное имя файла |
| `objectKey` | Ключ объекта в MinIO |
| `size` | Размер файла в байтах |
| `mimetype` | MIME-тип файла |
| `bucket` | Название bucket в MinIO |
| `createdAt` | Дата создания |
| `updatedAt` | Дата обновления |
| `deletedAt` | Дата удаления для Soft Delete |

Пример документа в MongoDB:

```json
{
  "_id": "1f3c7d38-6c33-4e9d-9f70-315c6c7f5f91",
  "userId": "b6f441c8-b909-4b6c-a628-98d7a3d44c71",
  "originalName": "avatar.jpg",
  "objectKey": "users/b6f441c8-b909-4b6c-a628-98d7a3d44c71/files/1f3c7d38-6c33-4e9d-9f70-315c6c7f5f91.jpg",
  "size": 512000,
  "mimetype": "image/jpeg",
  "bucket": "wp-labs-files",
  "createdAt": "2026-06-01T12:00:00",
  "updatedAt": "2026-06-01T12:00:00",
  "deletedAt": null
}
```

# Обновление модели пользователя

В модель пользователя добавлено поле `avatarFileId`.

```json
{
  "id": "user-id",
  "email": "user@example.com",
  "displayName": "User Name",
  "bio": "Описание профиля",
  "avatarFileId": "file-id"
}
```

При обновлении профиля система проверяет:

- авторизован ли пользователь;
- существует ли файл;
- принадлежит ли файл текущему пользователю;
- не удалён ли файл через Soft Delete;
- подходит ли файл для использования в качестве аватара.

---

# Валидация файлов

При загрузке выполняется проверка файла.

Ограничения:

| Проверка | Значение |
|---------|----------|
| Максимальный размер | 10 MB |
| Настройка размера | `MAX_FILE_SIZE` |
| Разрешённые MIME-типы для аватара | `image/png`, `image/jpeg`, `image/jpg` |
| Формат запроса | `multipart/form-data` |
| Буферизация в памяти | Запрещена |
| Обработка файла | Через Streams |

Если файл не проходит проверку, сервер возвращает ошибку `400 Bad Request`.

# API эндпоинты

## Файлы

| Метод | URI | Описание | Доступ |
|------|-----|----------|--------|
| `POST` | `/files` | Загрузка нового файла | Авторизованный пользователь |
| `GET` | `/files/<file_id>` | Скачивание файла по ID | Только владелец |
| `DELETE` | `/files/<file_id>` | Удаление файла | Только владелец |

## Профиль

| Метод | URI | Описание | Доступ |
|------|-----|----------|--------|
| `GET` | `/profile` | Получение текущего профиля | Авторизованный пользователь |
| `POST` | `/profile` | Обновление профиля и аватара | Авторизованный пользователь |

# Примеры запросов

## Регистрация пользователя

```bash
curl -X POST http://127.0.0.1:4200/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "123456",
    "displayName": "Test User"
  }'
```

## Авторизация пользователя

```bash
curl -X POST http://127.0.0.1:4200/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "123456"
  }'
```

После авторизации необходимо скопировать access token и использовать его в заголовке:

```http
Authorization: Bearer <access_token>
```

## Загрузка файла

```bash
curl -X POST http://127.0.0.1:4200/files \
  -H "Authorization: Bearer <access_token>" \
  -F "file=@avatar.png"
```

Пример ответа:

```json
{
  "id": "1f3c7d38-6c33-4e9d-9f70-315c6c7f5f91",
  "originalName": "avatar.png",
  "size": 245321,
  "mimetype": "image/png",
  "createdAt": "2026-06-01T12:00:00"
}
```

В ответе не возвращаются чувствительные поля `objectKey` и `bucket`.

## Скачивание файла

```bash
curl -X GET http://127.0.0.1:4200/files/1f3c7d38-6c33-4e9d-9f70-315c6c7f5f91 \
  -H "Authorization: Bearer <access_token>" \
  --output downloaded_avatar.png
```

При скачивании сервер устанавливает заголовки:

```http
Content-Type: image/png
Content-Disposition: attachment; filename="avatar.png"
Content-Length: 245321
```

## Удаление файла

```bash
curl -X DELETE http://127.0.0.1:4200/files/1f3c7d38-6c33-4e9d-9f70-315c6c7f5f91 \
  -H "Authorization: Bearer <access_token>"
```

Успешный ответ:

```http
204 No Content
```

## Обновление профиля с аватаром

```bash
curl -X POST http://127.0.0.1:4200/profile \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{

    "bio": "Профиль пользователя",
```

## Получение профиля

# Кеширование в Redis

Для ускорения получения метаданных файлов используется Redis.

Ключ кеша:

```text
wp:files:{fileId}:meta
```

TTL:

```text
300 секунд
```

Логика работы:

1. При запросе файла приложение сначала ищет метаданные в Redis.
2. Если данные найдены, они используются без обращения к MongoDB.
3. Если данных нет, приложение получает метаданные из MongoDB.
4. После получения из MongoDB данные сохраняются в Redis.
5. При удалении или изменении файла кеш инвалидируется.

# Сценарии тестирования

## 1. Загрузка корректного изображения

Ожидаемый результат:

- сервер возвращает `201 Created`;
- файл появляется в MinIO;
- метаданные сохраняются в MongoDB;
- ответ содержит id файла.

## 2. Загрузка файла больше 10 MB

Ожидаемый результат:

- сервер возвращает `400 Bad Request`;
- файл не загружается в MinIO;
- запись в MongoDB не создаётся.

## 3. Загрузка файла с запрещённым MIME-типом

Ожидаемый результат:

- сервер возвращает `400 Bad Request`;
- файл не сохраняется.

## 4. Скачивание своего файла

Ожидаемый результат:

- сервер возвращает `200 OK`;
- файл скачивается;
- установлены корректные заголовки `Content-Type`, `Content-Disposition`, `Content-Length`.

## 5. Попытка скачать чужой файл

Ожидаемый результат:

- сервер возвращает `403 Forbidden` или `404 Not Found`;
- файл не отдаётся пользователю.

## 6. Установка аватара

Ожидаемый результат:

- пользователь загружает изображение;
- получает `fileId`;
- отправляет `avatarFileId` в `/profile`;
- профиль обновляется.

## 7. Удаление файла

Ожидаемый результат:

- сервер возвращает `204 No Content`;
- файл помечается как удалённый;
- объект удаляется из MinIO или становится недоступным;
- кеш Redis очищается.

# Безопасность

В проекте реализованы следующие меры безопасности:

- доступ к файлам только по JWT;
- пользователь может получить только свои файлы;
- проверяется владелец файла;
- запрещено хранение файлов в папках приложения;
- запрещено хранение файлов в базе данных;
- секретные данные вынесены в `.env`;
- чувствительные поля `objectKey` и `bucket` не возвращаются клиенту;
- выполняется проверка MIME-типа;
- ограничивается максимальный размер файла;
- используется Soft Delete.
